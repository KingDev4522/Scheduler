# Master Product Requirements Document

## Problem and outcome (PS §1–2)
CIT (~1,000 students, three years, five branches) uses spreadsheets and calls/WhatsApp for scheduling. Week 7 creates pressure because regular classes continue, midsems follow next week and Spectra needs shared facilities. Deliver a unified web app generating conflict-free academic/exam schedules, prioritizing venue requests, repairing disruptions and explaining decisions.

## Users and jobs
- Admin: import data, generate/review schedules, approve changes, approve class-displacing bookings, configure priority order, export/reset.
- Department coordinator: request departmental changes/events and approve bookings of departmental labs, except own requests.
- Faculty: view own timetable, mark unavailability, request extra/moved sessions using form or assistant.
- Club representative: submit/cancel requests, see status and explanation.

## Functional requirements (PS §2)
- FR-01 Generate each of 189 sessions exactly once with day/start period/room and zero hard violations.
- FR-02 Schedule 41 midsem exams in following week; enforce half effective room capacity.
- FR-03 Parse English/Hinglish requests into editable structured booking drafts.
- FR-04 Evaluate all 25 Spectra requests including later cancellation, approve/reject/offer alternative with reason and priority.
- FR-05 Repair faculty leave, room closure and new session disruptions; minimize moved sessions, preview exact changes, Admin approve; explain infeasibility.
- FR-06 Student-group, faculty and room timetable views plus pending approvals, conflicts and utilisation.
- FR-07 Faculty AI scheduling assistant; deterministic validation of all proposals.
- FR-08 Evidence-grounded explanations for slot allocation and booking rejection.
- FR-09 Admin import original and change files; exact `schedule.json` export.
- FR-10 Authorized manual event scheduling obeys all hard constraints.

## Nonfunctional requirements
- NFR-01 Deployed application usable on laptop and phone, with loading/empty/error states (PS §8).
- NFR-02 All changes durable, auditable, and role-authorized (DESIGN supporting PS workflows).
- NFR-03 Manual booking usable during LLM outage (PS §6).
- NFR-04 Reproducible setup and validator-compatible exports (PS §7–8).
- NFR-05 No undocumented AI use; no secret keys committed (PS §6–7).

## Core journeys and acceptance
1. Admin uploads valid starter dataset -> receives import summary/errors -> generates timetable -> sees validator summary -> exports file; every session included once.
2. Club rep types Hinglish -> assistant extracts tentative fields -> user corrects them -> system checks constraints/priority -> request enters proper decision/approval flow -> reason visible.
3. Faculty requests leave -> system constructs candidate repair -> diff counts moved sessions -> Admin accepts/rejects -> state unchanged before approval.
4. Coordinator schedules lab event -> backend checks department ownership, non-self approval and hard constraints.
5. Judge logs into each role -> navigates timetable, rooms, approvals without guided walkthrough.

## Explicit exclusions / caution
No requirement for attendance, fee collection, student registration, payment, messaging, analytics beyond room utilisation, or autonomous AI authority. Do not expand scope before core validator and submission gates are satisfied.

## Definition of done
All 10 PS functions work in deployed app; both exports generated by app; official validator meets correctness targets; judge disruption processed; four accounts and reset work; <=5-minute video; complete declarations; no disqualifying conditions.


## Requirement provenance and decision policy
- **PS** = explicit requirement from the supplied six-page problem statement.
- **DESIGN** = proposed implementation, not an organizer mandate.
- **VERIFY** = unresolved until `cit_public.json`, starter-pack README, `validator.py`, and `sample_disruption.json` are inspected.
- Never fabricate or hand-edit generated schedules, booking decisions, exports, or demo outputs. Do not modify organizer validator files.
- All schedule/booking writes must pass deterministic hard-constraint and authorization checks. LLM output is untrusted input, never a validity oracle.
- Repository must be created after the hackathon starts; no pre-hackathon project code, purchased templates, or non-team developers. Declared AI tooling is allowed. No commits or deployment modifications after submission deadline.
