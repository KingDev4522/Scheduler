# Disruption Contract

**Status: authoritative.** Documented from `CrunchWeek_StarterPack/README.md` §"Disruption file format"
and `validator.py` `apply_disruption` (SHA-256 prefix `f02733b382fa111e`).

The practice file `examples/sample_disruption.json` uses the same format as the live judging file.

---

## 1. File shape

```json
{ "changes": [ { "type": "...", ... } ] }
```

Changes are applied **in order**. `apply_disruption` deep-copies the dataset, so the original file is
never mutated on disk.

## 2. Change types

### `faculty_unavailable`
```json
{"type":"faculty_unavailable","faculty_id":"F07","days":["MON"],
 "periods":[1,2,3,4,5,6,7,8,9],"reason":"Conference travel every Monday"}
```
Appends `{day, periods, reason}` to `faculty[faculty_id].unavailable` for every listed day → hard rule
`H7`. The faculty keeps their sessions; they must be taught at other times.

### `room_unavailable`
```json
{"type":"room_unavailable","room_id":"CR-102","days":["MON","TUE","WED","THU","FRI"],
 "periods":[1,2,3,4,5,6,7,8,9],"reason":"Water leak"}
```
Appends a `room_unavailability` row per day → hard rule `H8`.

### `add_faculty`
```json
{"type":"add_faculty","faculty":{ "...same shape as a faculty entry..." }}
```
Appends to `faculty` and registers it for later changes.

### `add_session`
```json
{"type":"add_session","session":{ "...same shape as a session...","fixed_slot":null }}
```
Appends to `sessions`. The new session must then be scheduled like any other.

### `remove_session`
```json
{"type":"remove_session","session_id":"HS201-H2-L2"}
```
Removes the session from `sessions`; it must not appear in the export.

Any other `type` raises `ValueError: Unknown change type` — the file is rejected, not partially
applied.

## 3. Semantics

- **Permanent:** "Changes are permanent: they hold for every week after they're applied."
- **Order matters:** a later change may rely on an earlier `add_faculty` / `add_session`.
- **Scoring:** the change file is applied to the data *before* validation, so the repaired export is
  scored against the disrupted dataset.
- **Baseline:** passing `--baseline schedule.json` adds the stability section, defining moved sessions
  as `(day, start, room)` changed (`docs/validator-contract.md` §7).

## 4. Sample file (practice)

`examples/sample_disruption.json` contains three changes:
1. `faculty_unavailable` F07 on `MON`, P1–P9 (conference travel).
2. `room_unavailable` `CR-102` `MON`–`FRI`, P1–P9 (water leak).
3. `add_session` `CS202-T2` (tutorial, group `CSE-2`, faculty `F06`, size 80, duration 1,
   room types `classroom/lecture_hall/auditorium`).

## 5. Required application behaviour (from the phase docs)

1. Validate the disruption schema before touching state.
2. Load the current published schedule.
3. Identify directly affected assignments.
4. Hold unaffected/fixed assignments where required.
5. Re-solve, preserving as many original assignments as possible.
6. Enforce every hard rule; validate the proposal independently.
7. Produce a diff of old vs new `(day, start, room)`.
8. Submit for Admin approval; **do not apply before approval**.
9. Record version, approver and audit history.
10. If no feasible repair exists: change nothing, report infeasible with the conflicting
    constraints, and never fabricate an explanation.

Moved sessions are minimised per the validator's definition (`docs/validator-contract.md` §7).

## 6. Current app support and gaps

| Capability | State |
|---|---|
| Faculty leave repair (internal model) | implemented (`repairTimetable`, `docs/agent/DECISIONS.md` DEC-009) |
| Room closure repair (internal model) | implemented |
| Official change-file parsing (`faculty_unavailable`, `room_unavailable`, …) | **not yet** — mapped in this contract, implementation is Phase 3 |
| `add_faculty`, `remove_session`, `add_session` | **not yet** |
| Permanence across weeks | not modelled (single-week model) |
| Baseline stability report | documented; produced by `validator.py`, not yet generated by the app |

The internal disruption types (`faculty_leave`, `room_closure`) correspond to the official
`faculty_unavailable` and `room_unavailable`; the engine already supports both as hard constraints
(`EngineInput.roomUnavailable`, `Faculty.unavailable`).
